# T01 status — recorder (done by the integrator after the Jules run failed)

## Delivered
* `recorder/src/os_mmap.{hpp,cpp}`: platform layer. POSIX (`open O_EXCL`, `posix_fallocate`; macOS `fcntl(F_PREALLOCATE)` then `ftruncate`; `mmap MAP_SHARED`, best-effort `mlock`, `msync`) and Windows (`CreateFile CREATE_NEW`, `SetEndOfFile` + zero fill when `reserve_disk`, `CreateFileMapping`, `MapViewOfFile`, `VirtualLock`, `FlushViewOfFile`). **The Windows branch has not been compiled or run** (no Windows build in CI yet); it was written against the Win32 documentation.
* `recorder/src/recorder.cpp`: `recorder_sizing`, `Recorder::create`, `open_readonly`, every virtual method of the contract. File header (256 bytes, `EYELIVE1`, version 1) with capacity, `count`, rate, scale, number of classes, class names (comma separated), flags (bit0 closed, bit1 scale estimated), creation time; state block region 256 bytes at offset 256 left zeroed (the recorder never reads it); arrays t, x, y, flags, label, expert, each starting on a multiple of 64; events table (`uint64 n_events` + 100 000 `Event` records of 72 bytes).
* Concurrency: `count` and `n_events` are published with release / acquire; `label` and `expert` are relaxed atomics (they may be written by another thread than the writer); single writer for `push` and `append_event`.
* Safety additions: `create` refuses to overwrite an existing file (`O_EXCL`), refuses sessions above 1 TiB before touching the disk (input error), removes the half-created file on failure; `open_readonly` validates magic, version and that the file is long enough for its declared capacity; after `close()` and on a read-only recorder `push` returns false.

## Measurements (Apple M1, Release, zig/clang)
| test | result |
|---|---|
| `recorder_sizing(1000, 3600)` | 3 781 024 samples, 78.24 MB = 19 B × samples + 512 + 8 + 100 000 × 72 B (matches the formula to 0.0 %) |
| crash (forked child writes 1e6 samples at full speed, no `close()`, no destructor) | all 1e6 samples, the event and the label intact after `open_readonly` |
| concurrent reader / writer, 2e6 samples (+ a third thread writing labels) | no torn read, reader saw every sample; same result under ThreadSanitizer, no warning |
| `push` returns false exactly at `count == capacity` | tested over `capacity + 5` calls |
| `create` errors | missing directory, impossible size (1e6 Hz × 1e9 s), invalid rate, existing file: all return a message, no exception |
| CSV round trip | `index,t,x,y,flags,label,expert`, 1000 samples bit-exact (`%.17g` for t, `%.9g` for x, y) |
| labels / expert / events / session info round trip, including after `close()` and `open_readonly` | exact |
| `push` throughput, single thread | 104.7 million samples/s (Release); 3.7 million/s under TSAN (limit 1e6) |

## Deviations and open points
* The task text says `recorder_sizing(1000, 3600).bytes` is "68 MB + table": 68 MB is 19 B × 3.6e6 samples without the 5 % margin. With the contract's default margin 1.05 the result is 71.8 MB of samples + 7.2 MB of table = 78.2 MB; the test checks the formula, not the 68 MB figure.
* `export_csv` writes the samples only (no events file).
* `lock_memory` is best effort and its outcome is not reported (the contract has no field for it).
* Windows branch untested (see above). On macOS the allocation uses `F_PREALLOCATE`; `posix_fallocate` is used on Linux (CI's Ubuntu runner exercises it).
